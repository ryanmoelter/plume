# Physical Android devices

A device tab (`TabKind.device`, platform `androidPhysical`) can mirror a physical Android device connected over adb, by USB or over Wi-Fi, and forward mouse, scroll and keyboard input to it. It runs [scrcpy](https://github.com/Genymobile/scrcpy)'s server on the device and speaks its protocol directly; Plume never runs the scrcpy client. Emulators use their gRPC service instead (`docs/android-emulator.md`). Both kinds share `DeviceSession`, the picker and the device view.

## Layout

- `Packages/ScrcpyControl/` holds the wire layer: `ScrcpyServerLaunch` (push, forward, run), `ScrcpyDemuxer`, `H264Decoder` (VideoToolbox, IOSurface-backed BGRA) and `ScrcpyControlMessage`. `ScrcpyConnection` is its facade. Run `swift test` in the package for its tests; `ScrcpyProbe` mirrors a real device for a few seconds without the app.
- `Plume/Android/PhysicalDeviceConnection.swift` adapts `ScrcpyConnection` to `DeviceConnecting`, the protocol the session talks to. `EmulatorDeviceConnection` is the emulator's adapter.
- `Shared/Android/ADBDeviceList.swift` lists devices from `adb devices -l`, and `Plume/Android/PhysicalDeviceDiscovery.swift` polls it while a picker is open.
- `Shared/Android/ADBWireless.swift` parses and runs the Wi-Fi commands (`adb mdns`, `pair`, `connect`, `getprop ro.serialno`). `Plume/Android/WirelessPairing.swift` drives a pairing, and `Plume/UI/Device/WirelessPairingSheet.swift` is its sheet.
- `Plume/Android/AndroidKeycodeMapper.swift` turns Mac key events into Android keycodes and text, tracks what the device holds, and decides which chords stay with Plume (`AndroidShortcutPolicy`).

## The server binary

`Plume/Resources/Scrcpy/scrcpy-server` is scrcpy's prebuilt server, pinned to `ScrcpyServerVersion.pinned` and stored in Git LFS. `scripts/android/fetch-scrcpy-server.sh` updates it; `scrcpy-VERSION.txt` records the version and checksum, and `scrcpy-LICENSE.txt` ships its Apache 2.0 license. The server checks that the client's version string matches its own exactly, so the binary and `pinned` move together.

- The file has **no `.jar` extension** on purpose: Xcode leaves a `.jar` in the synchronized group out of the bundle's `Resources`. The app finds it with `Bundle.main.url(forResource: "scrcpy-server", withExtension: nil)`.
- A checkout without `git lfs` has a pointer file there. `ScrcpyServerLaunch.verifyJar` catches that and the tab shows "is a Git LFS pointer … Run `git lfs pull`".

## Discovery

`AndroidSDKLocator` prefers an SDK with `emulator/emulator`, and otherwise takes the first candidate with `platform-tools/adb`. It looks for adb separately: the chosen SDK's own if it has one, else the first candidate that does. An adb-only install (Homebrew's `android-platform-tools`, say) therefore finds physical devices, and the picker reports that the emulator isn't installed. An SDK without `platform-tools/adb` still finds devices through another candidate's adb; only when no candidate has adb does the Devices section say adb wasn't found.

`PhysicalDeviceDiscovery` runs `adb devices -l` off the main actor every 2 seconds while the picker is on screen, and never otherwise. `emulator-*` serials are dropped, since emulators reach the picker through their discovery files. `unauthorized` and `offline` devices are listed but disabled, with a hint. The name is the `model:` field with underscores turned into spaces, or the serial.

## Wi-Fi

**Pair over Wi-Fi…** in the picker's Physical devices section opens a sheet with two ways to pair, both from Settings ▸ Developer options ▸ Wireless debugging on the phone. The phone and the Mac must share a network.

- **QR code.** Plume shows `WIFI:T:ADB;S:<name>;P:<password>;;`, with a fresh random `plume-<hex>` name and hex password each time (`ADBPairingQR`). Scanning it makes the phone advertise a `_adb-tls-pairing._tcp` service under that name. Plume polls `adb mdns services` every second for it, then runs `adb pair <address> <password>`. This needs adb's mDNS, so the sheet first runs `adb mdns check`. When that fails, it says so and points to the pairing code instead.
- **Pairing code.** The user types the IP address and port and the six-digit code from Pair device with pairing code, and Plume runs `adb pair`. An optional third field takes the IP address and port from the main Wireless debugging screen, which Plume needs to connect when adb's mDNS can't see the phone. Its placeholder carries the pairing address's host, since the phone listens on the same host at another port.

adb exits 0 from a failed `connect`, and `pair`'s exit status varies, so Plume reads the text: `Successfully paired`, `connected to`, `already connected to`. A `protocol fault` or `Unable to start pairing client` from `pair` reads as "Couldn't reach the device's pairing service", with a hint to check the address, the code and that the dialog is still open. Any other failure shows adb's own last line.

After a pair, adb normally connects the phone by itself through mDNS, as `adb-<serialno>-<suffix>._adb-tls-connect._tcp`. Plume polls `adb devices` and `adb mdns services` every second for the phone: a ready Wi-Fi device whose `host:port` serial is on the host it paired with, or whose mDNS serial names a `_adb-tls-connect._tcp` service on that host. A phone already connected counts, so pairing one again finds it. Plume runs `adb connect` itself only where adb can't:

- While mDNS shows a connect service on that host, Plume leaves the connecting to adb for 14 seconds (`autoConnectWindow`). An `adb connect` of its own would add a second transport for the same phone. After that, it connects each such service once.
- Without a connect service, adb never connects the phone. Plume connects to the entered Wireless debugging address once, after 3 seconds.

After 20 seconds without the phone, the sheet shows `pairedNotConnected`: the pair worked, so it asks only for the Wireless debugging address, with a **Connect** button that skips pairing. Connect runs `adb connect` on the typed address at once, then waits for the phone. In that phase Return connects rather than pairs, since the phone has dropped the pairing code; editing the pairing address or code hands Return back to Pair. Once connected, the picker closes the sheet and, from the sheet's `onDismiss`, connects the device like a picked one. Connecting first would replace the picker, which owns the sheet.

A device is on Wi-Fi when its serial is `host:port` or names `_adb-tls-connect._tcp`. A remote device's `localhost:` serial is a tunnel, not Wi-Fi, and `DevicePool` still classifies a LAN serial as physical. The picker shows each device's transport in its detail line, and one row per phone (`phones(in:)`): a phone adb lists over USB and Wi-Fi, or under both an mDNS name and an address, shows its ready connection, preferring USB, then the mDNS name.

### Identity

A Wi-Fi serial changes with every connection, so a tab can't persist it. Discovery reads each ready Wi-Fi device's `ro.serialno` once per connection (`adb -s <serial> shell getprop ro.serialno`, off the main actor) and caches it by adb serial until adb stops listing that serial. A failed read is tried again by a poll only after 8 seconds (`serialRetryDelay`). `resolvedIdentifier(forSerial:)` and a session's locate (`refresh(retryingFailedReads: true)`) try again at once, since they are about to persist an identifier or say the phone isn't there. A read already running survives a listing that doesn't name its serial. Discovery also remembers, in memory and for the last 64 Wi-Fi serials, the serial number of each one adb has stopped listing, so a tab saved under a phone's old address still names that phone. `adb get-serialno` won't do: it answers with the transport's serial, the address or mDNS name. Discovery publishes the device list before these reads finish, and drops a listing older than one it already published. A refresh whose listing was dropped still waits for the reads of the newer one. Picking a Wi-Fi device resolves its serial number before the tab persists anything, so a tab connected to a Wi-Fi device persists `wifi:<serialno>` in `deviceIdentifier`. If that read fails, the tab persists the address, and the next locate that reads the serial number rewrites it to `wifi:<serialno>`. A pick cancelled mid-read leaves the tab with no device. A USB tab persists its adb serial as before, which is the same serial number.

On start, `PhysicalDeviceDiscovery.readySerial(for:)` maps the identifier to the adb serial to connect to now. An exact serial wins. Otherwise a ready device with that serial number does, on Wi-Fi first for a `wifi:` identifier and on USB first for a plain one. So a `wifi:` tab also finds the phone plugged in over USB. A Wi-Fi tab whose phone isn't listed says to turn on Wireless debugging; **Try Again** lists adb again, and adb reconnects a paired phone on its own once Wireless debugging is back on. That needs adb's mDNS, so the session runs `adb mdns check` then, and when it fails the tab says to pair or connect again from **Change Device…**. `devices.show` from `plume devices` maps a Wi-Fi serial to its `wifi:` identifier the same way, reading the serial number on the spot if discovery hasn't. It matches tabs by serial number (`namesSamePhone`), so it finds the tab already showing that phone, whether that tab is on USB, on `wifi:`, or saved under an older Wi-Fi address. `DeviceSession.point(at:)` matches the same way, so a matched tab that isn't running looks for its phone again. Leases still key on the adb serial.

The scrcpy path is unchanged: `adb -s <host:port>` push, forward and shell work over TCP as over USB.

## Connecting

The tab persists `devicePlatformRaw = "androidPhysical"` and the adb serial in `deviceIdentifier`, or `wifi:<serialno>` for a Wi-Fi device (see Identity above). A tab from before physical devices has `androidEmulator` and an AVD id, and still resolves to an emulator; so does a tab with an identifier but no platform.

Picking a device in the picker connects at once, since the picker's adb list is current. On start, the session refreshes the adb list. If the serial is missing or not `device`, it shows "isn't connected" with **Try Again**, which looks again. If the device is ready but no sink is attached, as for a hidden tab in a shown task, the session goes straight to `.suspended` without connecting, and the first sink connects. Otherwise `ScrcpyConnection.connect()`:

1. pushes the server to `/data/local/tmp/plume-scrcpy-server-<scid>.jar`, a path per launch so two tabs on one device never overwrite each other's jar (`cleanup=true` deletes it),
2. runs `adb forward tcp:0 localabstract:scrcpy_<scid>`, where the scid is random,
3. starts the server with `adb shell app_process` (H.264, no audio, control on, `tunnel_forward=true`, `clipboard_autosync=false` since Plume never reads the device clipboard; setting it, for a paste, works without autosync),
4. retries the video socket until the server sends its dummy byte (a forward accepts before the server listens), then opens the control socket,
5. reads the device name, codec and the initial video size.

A start that doesn't end with the server running (a failed or timed-out push or forward, an unparsable port, a stop, a failed spawn) runs `adb shell rm -f` on the pushed jar, on a background queue joined to the quit-time wait like the forward cleanup. Only a running server's `cleanup=true` deletes it otherwise.

Every adb command has a deadline: 30 seconds for the push and 5 for each forward command. A command that misses it is killed, and the tab shows the failure with **Reconnect**. Cancelling the connect kills the command in flight too. A killed `forward` may still have created the forward on a port nobody read, so the launch then runs `adb forward --list` and removes every entry pointing at its `localabstract:scrcpy_<scid>`. That cleanup, like every forward removal, runs on a background queue rather than as a cancellable command, so a cancelled connect still completes it. The launch joins the quit-time wait from before `adb forward` runs until its forward is either recorded or removed, so a quit mid-forward waits for that cleanup too.

Closing the session (closing the tab, `TaskStore.forgetTab`, or the idle stop) stops the server and removes the forward. The session starts that stop synchronously, through the connection's `terminate()`, before the asynchronous `close()` tears down the sockets, so a quit straight after a close still waits for it. `ScrcpyServerLaunch.stop()` is safe at any point: a close during the push or the forward releases whatever exists by then, and the launch then creates nothing more. Nothing ever powers a physical device off: the shut-down item is hidden for it in both the device view and the tab-strip menu.

On quit, `DeviceSessionManager.terminateAll()` starts each stop without waiting, and `applicationWillTerminate` then blocks in `DeviceSessionManager.awaitTerminations()`, alongside `AgentProcess.awaitTerminations()`, until the `adb shell` children have exited and the forwards are gone. The wait is bounded at a few seconds.

## Frames

- The device encodes at its native size. **A resize never restarts the stream**; the layer's `resizeAspect` scales it. (Emulators restart at the largest requested size instead.)
- Frames arrive already rotated, so the session reports every physical frame as `.portrait`.
- `DeviceFrame` carries an IOSurface for physical frames and a `CGImage` for emulator frames. The surface view sets either as `layer.contents` and holds the frame until the next one, which keeps the pixel buffer that owns the surface alive.
- scrcpy sends a frame only when the screen changes. The session keeps the last frame and hands it to a sink that attaches mid-stream, so a tab shown again within the grace period doesn't stay black on a static screen.
- A config packet the decoder rejects, or a frame it fails to decode (including one VideoToolbox returns with no image and no error), costs frames, not the connection. The decoder drops frames until the next key frame, and the pump sends `RESET_VIDEO` for one, at most once a second until a frame decodes (`KeyFrameRecovery`). If nothing decodes for 10 seconds, the stream ends with "The device's video couldn't be decoded", and the tab offers **Reconnect**.

## Hidden tabs and the grace period

A physical tab stays connected for `DeviceSession.physicalIdleStopDelay` (5 seconds) after its last sink leaves, or after a connect that finishes with no sink, as a picker's connect can. A sink returning within that time cancels the stop and keeps the same connection and stream. Once the delay expires the session closes the connection, which stops the server and removes the forward, so a hidden tab never keeps the phone encoding. The session's state is then `.suspended`, which is not an error and offers no button. The next sink to attach reconnects to the same device, which takes about a second. Emulators stop streaming at once and keep their connection.

**Turn Off Streaming** in the ellipsis menu does the same at once, with no delay, for a physical or remote tab. The state is `.streamingPaused`, in memory only. A returning sink does not reconnect from it; **Turn On Streaming** or the card's **Re-enable streaming** does. Changing device clears it.

Reconnecting costs about a second and a visible stall, which a quick tab switch shouldn't pay. The delay is injected (`idleSleep`), so tests fire it by hand rather than waiting on a clock.

## Input

- **Coordinates.** A touch is in current video pixels, sent with that video size (`ScrcpyPosition`). The server drops any event whose size differs from its current one, so a touch that races a rotation vanishes instead of landing in the wrong place. The session sets `deviceSize` from each frame's video size, and the surface sends the size it mapped the point against, so `DeviceCoordinateMapper` needs nothing physical-specific.
- **Touches** go as `injectTouch` with the generic finger pointer id: down, moves, up; pressure 1, then 0 on up.
- **Scroll** goes as `injectScroll` at the pointer, one unit per notch (`WheelAccumulator`'s 120 units divided by 120). A wheel off the screen is dropped, since the server scrolls at a position.
- **Keys.** Plume follows the scrcpy client's default keyboard exactly where AppKit allows: the SDK keyboard with "mixed" key injection (`keyboard_input_mode` resolves from `AUTO` to `SDK` in `app/src/cli.c`, `key_inject_mode` defaults to `MIXED` in `app/src/options.c`; the mapping is `convert_keycode` and `sc_key_processor_process_text` in `app/src/keyboard_sdk.c`).
  - Letters and space go as keycodes with their meta state, so Shift-A is KEYCODE_A with Shift and Control-C is KEYCODE_C with Control. The letter comes from `charactersIgnoringModifiers`, which follows the keyboard layout the way SDL's keysyms do, so an AZERTY "a" sends KEYCODE_A.
  - Return, keypad Enter, Tab, Delete, Forward Delete, Escape, the arrows, Home, End, Page Up and Page Down always go as keycodes (so Shift-Tab works).
  - Shift, Control, Option and ⌘ go down and up on their own as the Mac reports them, left and right separately (⌘ is Android's Meta), and the meta state carries the side bits (`META_SHIFT_LEFT_ON`, `META_ALT_RIGHT_ON` and so on) from the event's device-dependent flags. Caps Lock is a meta bit only; its key, like fn, is not forwarded.
  - A key's text goes as `injectText` unless it starts with an ASCII letter or space, or ⌘ is held (SDL sends no text for a ⌘ chord). So digits, punctuation, accented and non-Latin letters go as text, and a key can send both: Option-A sends KEYCODE_A with Alt and the text "å". A dead key sends only its keycode, and the next key sends its own keycode plus the composed character, so Option-E then E sends KEYCODE_E with Alt, KEYCODE_E and "é". That doubles on some apps, and is scrcpy's documented tradeoff for mixed mode (`doc/keyboard.md`, "Text injection preference"). Function keys are not forwarded.
  - A held key's auto-repeats go as further key-downs with a rising repeat count, which the release resets; a held text key sends its text again.
  - `AndroidPressedKeys` tracks what the device holds and routes each release by what its press sent, not by the modifiers held at release: a Control-C whose Control is let go first still releases KEYCODE_C. A release with no matching press sends nothing. A key-down first brings the device's modifiers in line with the event's flags, so a modifier held before the view had focus goes down with the next key.
  - **⌘ chords.** scrcpy keeps Left ⌘ and Left Option for its own shortcuts; Plume keeps its own shortcuts instead, the ones `TerminalShortcutMonitor.isClaimed` matches (`PlumeShortcuts.all` plus ⌘, ⌘H ⌘Q), and forwards every other key. A ⌘ chord that isn't one goes to the device as Meta plus the key: `DeviceSurfaceView.performKeyEquivalent` takes it ahead of the menu bar, so Edit and Window items such as ⌘C or ⌘M go to the device too. ⌘V is the exception: it pastes the Mac's clipboard (see **Paste** below). A lone ⌘ press and release reaches the device as a Meta tap, which opens All Apps on a Pixel.
  - AppKit sends no `keyUp(with:)` for a key released while ⌘ is held. While the surface is first responder, a local `keyUp` monitor catches the real release of any key the device holds, sends it, and consumes the event so it isn't sent twice. As a fallback, releasing ⌘ first releases every key that went down while it was held.
  - When a Plume shortcut fires, the surface first releases everything the device holds (`AndroidPressedKeys.releaseAll`), so the device never keeps Meta down; the shortcut's own key is not forwarded. The surface releases everything the same way when it loses first responder or its window resigns key (a ⌘Tab away never delivers ⌘'s release), and sends the old session the same releases when it changes sessions or detaches. Android opens All Apps on a Meta release with no other key since its press (`mPendingMetaAction` in AOSP's `KeyGestureController.interceptSystemKeysAndShortcuts`, and `PhoneWindowManager` before it), and only a release flagged canceled skips that, which scrcpy's inject message can't express. So when Meta is all that is held, `releaseAll` sends a Control press and release first, which cancels the action and does nothing else. This is from reading AOSP, not measured on a device.
  - Settings ▸ Shortcuts ▸ Devices ▸ "Intercept Plume keyboard shortcuts" (`AppSettings.keepsPlumeShortcutsOnMac`, on by default) turned off hands the device every ⌘ chord, Plume's own included. The surface tells `TerminalShortcutMonitor` to leave the chord alone through `MenuShortcutYielding`, then takes it in `performKeyEquivalent`. A Plume shortcut without ⌘ (a rebound Option chord) stays on the Mac either way. All of this is physical devices only; emulator tabs keep their own mapping (`EmulatorKeyMapper`), and ⌘ chords stay with the menus there, except ⌘V, which pastes (`docs/android-emulator.md`).
- **Paste.** ⌘V and Edit ▸ Paste send the Mac clipboard's text as one `setClipboard` message with `paste` set, so the server sets the device clipboard and presses KEYCODE_PASTE (Android 7 and later), the way the scrcpy client's own paste works. ⌘V is taken in `performKeyEquivalent` whatever "Intercept Plume keyboard shortcuts" says, unless it is bound to a Plume shortcut that stays on the Mac, and is consumed even when the clipboard holds no text, so it never reaches the device as Meta+V. ⌘⇧V and other chords with V still go as Meta plus the key. Every ⌘V first releases everything the device holds (`releaseAll`), with or without text, so the Meta that ⌘ put down is up before the paste and the later ⌘ release is no lone Meta tap. A held ⌘V's auto-repeats paste nothing more. Text over scrcpy's limit, 256 KiB less a 14-byte header, is cut at a character boundary. Only text is pasted, and nothing comes back from the device's clipboard.
- **Buttons.** Back is `backOrScreenOn`, which wakes a sleeping screen. Home, Overview, Power and the volume keys are keycodes, down then up.
- **Rotate** has no button for a USB device. A phone turns with its own sensor and auto-rotate setting, and the stream follows. A remote device (`docs/android-remote-device.md`) has one Rotate button, since nobody can turn it; `PhysicalDeviceConnection.rotate` turns auto-rotate off, then sends `rotateDevice`, which only toggles between portrait and landscape.

## Logging

Physical sessions log through `EmulatorLog`, under the `emulator` category, like emulators.
